## Architecture decisions and release states

1. **Use one server-side catalog composed from small authored project modules.** A discriminated union separates rich flagship records from retained legacy secondary records, collection records, and homepage-only records. It supplies typed, allowlisted projections for homepage proof, Work cards, related links, metadata, and case-study shells. Client components receive only the projection for their surface and the selected detail page's approved fixture; they never import the catalog or unrelated narratives, transcripts, or fixtures. Never spread a research record into props. Test both the input schema and serialized responses; server placement alone does not prevent leaks.
2. **Use five small state models, not a generic workflow interpreter.** Share presentation controls and media, while Vora authorization branches and Prism receipt ordering remain project-specific. Reducers and selectors are pure, testable in the existing Node Vitest environment. No DOM testing package is needed for those tests.
3. **Preserve explicit routes and the legacy `WorkDetail` API.** Add a rich-project branch to the component. ChapterHQ and the site assistant remain legacy secondary records with their current bodies and fields; they are never required to invent flagship story, evidence, interaction, or maturity data. Real Estate Maite remains a homepage-only record with no detail route. Never map `Implemented` to `live`. Keep the Open source collection outside the main result set.
4. **Resolve publication through one explicit public-view state machine.** For migrated Vora, model `legacy`, `rich-draft-with-legacy-fallback`, and `rich-published`. The first two production states render the existing legacy body at `/work/vora`; the third atomically renders the approved rich body. Rolling back the rich state restores the legacy body at the same URL. For a new flagship, draft resolves to production 404 and published resolves to rich only when its route is in the checked known-route registry. Metadata, catalog counts, cards, related links, and sitemap consume this resolved production view rather than raw flags. Local development may render a visibly labeled rich draft through a separate preview selector; no URL parameter, cookie, or deployed switch enables it.
5. **Bind evidence review to immutable bytes.** Every approved fixture/evidence snapshot records a SHA-256 digest of each exact checked-in fixture source and media file, plus derivation, checked date, disclosure, and its allowlisted public fields. An immutable upstream revision is additional context, never a substitute for the digest of the actual public sample. Interactions reference the snapshot ID. Schema/build tests recalculate local digests and fail after any fixture mutation until a reviewer updates the manifest and attestation. Local development may use explicitly illustrative samples, but they do not become production fixtures by placement alone.
6. **Publish only reviewed inert assets.** The checked-in root `showcase-evidence.manifest.json` is the single reviewed manifest for fixture source files and media. Each snapshot lists exact relative paths, SHA-256 digests, verified media/data types, derivation, checked date, disclosure, and allowed public fields. The actual typed catalog references snapshot IDs; the shared public-view selector derives which snapshot/media files the current production build requires, so the manifest never duplicates mutable publication flags. The prebuild gate fails for an unlisted, missing, stale, changed, draft-only, path-escaping, symlinked, extension/type-mismatched, or undecodable file under `public/work/**`, while leaving unrelated existing `public/**` files outside this gate. Allowed images are PNG, JPEG, WebP, and AVIF; allowed video is MP4 and WebM. HTML, SVG, XML, arbitrary JSON downloads, and other active documents cannot be same-origin showcase media or open-image destinations. Unapproved captures and source material remain outside the website repository and its build inputs until reviewed.

Do not copy private project code, run logs, configs, captures, internal paths, hostnames, or customer records into the website. Private evidence remains in the research ledger. Only independently reviewed, purpose-written public strings/assets enter application modules or browser fixtures. Do not add build-time reads of private/external source repositories or arbitrary HTML/script content. Reading this website's typed catalog, evidence manifest, fixture sources, and `public/work/**` for the in-scope validation gate is required.
